# ZhaoXi / Kuai Dao 19.0.0 Authoritative Backend Full Source Audit

Audit date: 2026-08-15
Repository: `D:\App Giao hàng\kuai-dao-backend`
Audited branch: `main`
Audited commit: `2c7dfd59c9cda3c20c752ba91ce30a863f70530d` (`ZhaoXi 18.1.1: synchronize backend release metadata`)
Audit mode: source-only, read-only, no database access, no external requests, no migration execution, no deployment
Release decision: **BLOCKED**

Classification used in this report:

- **MATCH**: the source supplies the expected capability with a coherent data and security path.
- **PARTIAL**: meaningful implementation exists, but important lifecycle, integrity, security, or operational elements are missing.
- **STUB**: routing/catalog scaffolding exists without a production-complete domain model and lifecycle.
- **ABSENT**: no material backend implementation was found.

## 1. Executive Summary

The backend is a substantial Next.js/PostgreSQL application: 268 App Router API route files, 90 Drizzle table declarations, unified bearer sessions, WeChat OAuth, customer/partner/driver/admin surfaces, generic service requests, delivery, payments, support, operational controls, and 120 release-oriented verification scripts. Platform route availability is broad: all 118 expected Platform upstream API families have a corresponding backend family.

It is not safe to release as 19.0.0. Eight P0 findings block production. The largest issues are unauthenticated legacy read/write endpoints, cross-tenant mutation paths, non-convergent migrations, support/payment exposure, and non-atomic financial and request transitions. Newer role-specific route families often enforce role and tenant membership correctly, but the reachable legacy routes bypass those controls.

The canonical migration path creates 18 tables while the declared runtime schema contains 90. The remaining schema is distributed across 51 separately invoked release migration scripts without a unified ledger or deterministic all-migrations runner. A fresh database cannot be shown from source to converge through `npm run db:migrate`.

Authentication fundamentals are stronger than most other areas: random opaque access/refresh tokens are hashed at rest; expiries, logout, device revocation, OAuth state, QR exchange TTLs, WeChat response timeouts, and constant-time comparisons exist. However, refresh-token rotation and WeChat exchange consumption are select-then-update operations without compare-and-set, leaving concurrent replay windows. There is no centralized authorization middleware, rate limiting, or systematic input schema validation.

The recommended 19.0.0 direction is a modular monolith with centralized authentication/authorization, explicit tenant-scoped repositories, convergent ledgered migrations, transactional state-machine commands, an outbox-backed worker, immutable financial ledger entries, idempotency records, and normalized vertical-domain data. The first implementation sprint must close exposed legacy endpoints and establish migration truth before feature expansion.

## 4. Database Architecture

The 90 declared tables cover identity, organizations, generic services and requests, customer preferences, delivery, payments, support, release controls, restaurant settlement, CRM, and operations workflow. Core relationships use foreign keys and several useful unique/index constraints.

Strengths include unique request codes, unique payment idempotency keys, a unique delivery job per request, composite organization membership keys, hashed session credentials, and append-oriented request/payment event tables.

Material gaps:

- No database row-level security was found; all tenant isolation depends on application code.
- `wechat_union_id` is not unique, leaving identity-link collision risk.
- Payment provider references and webhook event identifiers are not uniquely constrained.
- No immutable double-entry ledger, refund entity, payout entity, order-item model, catalog/menu model, vehicle inventory model, visa case model, translation job model, community post model, marketplace order model, or emergency incident model exists.
- Generic JSONB fields hold financially and operationally important vertical state, reducing constraints, queryability, and safe concurrency.
- The request status history is not transactionally coupled to every request mutation.
- Money representation is inconsistent: `numeric(14,2)` for core payments and integer units for partner transactions/settlements.

## 5. Migration Convergence

**Classification: NON-CONVERGENT — P0 release blocker.**

Evidence:

- `npm run db:migrate` invokes Drizzle against five canonical SQL files.
- Those five files create only 18 of the 90 declared tables.
- The repository also contains 51 `scripts/migrate-*.mjs` files.
- Static extraction finds 72 additional table creations in those manual scripts.
- There is no single ordered runner, shared migration ledger, checksum validation, or documented fresh-database replay path spanning both systems.
- Many manual scripts are idempotent at individual statement level, but idempotence does not establish correct total order or schema equivalence.
- The root `schema.ts` and canonical `db/schema.ts` have different SHA-256 hashes.

The actual production schema was not queried, so production drift cannot be measured. Source alone proves that canonical migration replay is insufficient. Before implementation, snapshot production metadata read-only, reconcile it against `db/schema.ts`, create one reviewed baseline/forward chain, and prove both fresh install and production upgrade in disposable databases.

## 6. Authentication

Opaque access and refresh tokens are generated from cryptographically secure random bytes and stored only as SHA-256 hashes. Access tokens expire after 15 minutes; refresh lifetimes differ by role. Session status, logout, logout-all, device listing, and device revocation exist. Trusted-device and QR-pairing records carry expiry/revocation state.

Weaknesses:

- Refresh rotation selects a valid row and then updates only by session ID. Two concurrent uses of one refresh token can both pass and mint valid-looking results; the later write wins in storage.
- Authentication updates `lastSeenAt` on every accepted request, adding write load to all protected traffic.
- There is no rate limiter for login, exchange, refresh, guest bootstrap, or admin access-card attempts.
- Admin access cards depend on configured hashes but have no attempt throttling, lockout, step-up, or fine-grained admin permission model.
- Bearer authentication avoids classic backend cookie CSRF, but any Platform BFF cookie boundary still requires its own CSRF review.

Classification: **PARTIAL**.

## 7. WeChat

The OAuth flow uses a 32-byte random state stored in `wechat_login_sessions`, checks expiry/status, exchanges authorization code with WeChat, uses 8-second upstream timeouts, binds OpenID/UnionID, applies role/allow-list decisions, and generates a short-lived random exchange code stored as a hash. Code comparison is constant-time.

The exchange consumer performs a read/check followed by an update matched only on session ID. Concurrent consumers can both validate before either clears the hash. The update must atomically require `exchanged_at IS NULL`, the expected code hash, valid expiry, and confirmed state, returning exactly one winner. UnionID should also be uniquely constrained where present after collision reconciliation.

Provider failure is converted to route failure, but there is no circuit breaker or durable recovery workflow. Classification: **PARTIAL**.

## 8. Authorization

Newer customer routes generally require `customer`; partner routes generally require `partner` and organization membership; driver routes require `driver`; admin routes require exact `admin`. These checks show the intended policy.

The policy is not centralized. Confirmed bypasses include:

- Unauthenticated request lookup/listing by ID, phone, or request code.
- Unauthenticated request assignment and status mutation, including a `force` transition bypass.
- Unauthenticated organization, service, and media mutations using caller-supplied organization IDs.
- Unauthenticated payment reads/creation/native checkout; payment status mutation by any admin, partner, or driver without entity scope.
- Unauthenticated support conversation access/response/escalation by supplied ID.
- Unauthenticated analytics, observability reads, and generic notification audience queries.
- Public delivery tracking by request ID without an ownership capability.

Classification: **BROKEN at the reachable system boundary**, despite stronger isolated route families.

## 9. Tenant Isolation

Tenant isolation is application-only; no PostgreSQL RLS or mandatory scoped repository abstraction exists. Newer partner services often verify active `organization_members` and request assignment. Legacy services/media/organization/payment/support handlers accept tenant or entity identifiers directly and allow cross-tenant reads or writes.

The effective result is **WEAK/PARTIAL**. Every organization-owned query and command should receive an authenticated tenant context from the server, never a trusted tenant ID from request input. Defense-in-depth RLS should be evaluated after the application policy is made explicit.

## 10. Request/Order State Machines

The generic request states are `new`, `reviewing`, `assigned`, `accepted`, `in_progress`, `waiting_customer`, `completed`, `cancelled`, and `rejected`, with an explicit transition map. Delivery separately uses `searching_driver`, `assigned`, `picked_up`, `delivering`, `delivered`, and `cancelled`.

The model is undermined by the unauthenticated `force` status path. Normal request status updates read state, update by ID, and insert history without a transaction or compare-and-set predicate. Concurrent commands can both validate against stale state and produce lost transitions or history divergence. Assignment has the same defect. State commands need authorization, expected-version/state predicates, transactional history, and immutable actor/reason metadata.

## 11. Idempotency

Core payment creation has a deterministic unique key per request/method. Partner payment transactions also carry a unique idempotency key. These are useful beginnings.

Request creation, message send, assignment, status change, coupon flows, settlement transitions, refunds, and most admin commands do not accept or persist an idempotency key. Core payment creation uses select-then-insert, so a concurrent duplicate can surface as a uniqueness error instead of returning the existing result. There is no general idempotency record with request hash, response snapshot, expiry, and conflict semantics.

Classification: **PARTIAL**.

## 12. Payment Architecture

Two payment concepts coexist:

- Core `payment_transactions` with WeChat Pay v3 native checkout and webhook handling.
- Partner gateway transactions designed for direct-to-partner payment, explicitly recording that the platform does not hold funds.

WeChat request signing, response verification, platform certificate serial validation, AES-GCM decryption, merchant/app/currency/amount matching, and raw-body webhook signature verification are implemented. Partner gateways use configured secret references and HMAC verification.

Critical gaps are unauthenticated payment endpoints, cross-tenant status mutation, missing durable refund/payout lifecycles, missing webhook replay controls, inconsistent money units, and non-atomic propagation into request state. Classification: **PARTIAL; not ready for real-money production**.

## 13. Payment Accounting

`payment_events` is append-oriented, but it is not an accounting ledger. Payment state remains a mutable aggregate row. Restaurant settlements snapshot completed food orders and calculate commission/payable values, but settlement transitions and adjustments are not consistently transactional or compare-and-set protected. Paid status can be marked administratively without a payout-provider proof.

There is no double-entry journal, balance invariant, receivable/payable separation, provider clearing account, refund amount tracking, partial refund allocation, chargeback model, or reconciliation exception closure linked to immutable postings. Financial integrity is **STUB/PARTIAL**, not ledger-grade.

## 14. Webhook Security

WeChat webhook cryptography is materially correct, but timestamp freshness is not enforced and notification nonce/event IDs are not persisted uniquely. A captured valid notification can be replayed; duplicate success deliveries append duplicate payment events. Partner webhook HMAC validation similarly lacks timestamp freshness and a durable replay key.

Required controls are bounded timestamp skew, unique provider event/transaction identifiers, atomic insert-if-new, raw payload hash retention, safe duplicate acknowledgement, and transactionally coupled state transition/outbox publication.

## 15. Messaging Durability

Normalized customer support thread/message tables exist and newer customer/partner message-center services bind ownership. Housing, travel, and payment-support conversations also store message arrays inside `service_requests.details` JSONB, often with capped history.

JSON array read-modify-write has no version predicate and can lose concurrent messages or read receipts. Message send is generally not idempotent, pagination is limited, and multi-write thread/message/event updates are not consistently transactional. There is no broker, outbox, delivery receipt pipeline, or WebSocket/SSE channel; clients poll HTTP.

Classification: **PARTIAL**.

## 16. Notifications

Customer notifications are derived from request history and saved-search events, with persisted preferences, receipts, read state, and customer ownership on the newer API. The generic notifications endpoint is unauthenticated and accepts privileged audience selectors.

No email, SMS, mobile push, or WeChat notification delivery provider was found. Some GET paths synchronously execute expiry/reminder/payment automation. There is no durable queue, retry schedule, dead-letter store, provider delivery record, or backpressure. Classification: **in-app PARTIAL; external delivery ABSENT**.

## 17. Support/Emergency

Support includes normalized threads/messages, SLA policies/events, tags, internal notes, macros, knowledge articles, feedback, satisfaction, CRM, automation rules, and an optional AI assist endpoint with a 12-second timeout and deterministic fallback. Newer customer support paths are scoped.

The legacy support route permits conversation IDOR and arbitrary response/escalation. Its assistant path can include order context such as address/details in a configured external AI request without proving ownership. Paid-human-support configuration does not establish a complete billing lifecycle.

Emergency is only a seeded generic module/service route. No emergency incident, dispatch, responder, acknowledgement, escalation clock, evidence, location-sharing consent, or safety audit model was found. Support is **PARTIAL**; emergency is **STUB**.

Public tracking accepts a request ID without authorization/capability. ## 26. Admin/Operations

Admin routes commonly require exact `admin`. The backend includes feature flags, runtime controls, release approvals/incidents/audits, rollout guard policies/events, UI acceptance, operations command center, routing, playbooks, workflows, approvals, CRM, support desk, settlement, compliance, quality, and payment operations.

Permissions are coarse: any admin can generally perform any admin action. High-risk actions lack step-up authentication, dual control, reason requirements, and universal tamper-resistant audit linkage. Some global analytics/observability views remain public. Classification: **PARTIAL**.

## 27. Media Security

Media asset records store organization, URL, type, size, and metadata. Backend media create/update/delete handlers are unauthenticated and trust caller-supplied organization, URL, MIME, and size. Actual upload bytes are handled elsewhere, so backend source provides no proof of content scanning, allow-listed storage origin, signed upload policy, image re-encoding, malware detection, or private-object authorization.

Classification: **BROKEN for mutation authorization; upload security unverified**.

## 28. Input Validation

There is no schema-validation dependency such as Zod. Of 268 routes, 132 parse JSON and only four import the shared validation helper. Most validation is manual and inconsistent; many handlers spread arbitrary JSON into metadata/details or pass identifiers directly to services.

Required improvement: versioned request/response schemas at every boundary, strict unknown-field policy for commands, length/range/enum/URL validation, normalized phone/currency/time handling, and safe error mapping. Classification: **WEAK**.

## 29. Security Findings

The dominant risk is broken object-level and function-level authorization, not SQL injection. Drizzle parameterization and tagged SQL are used; no clear attacker-controlled raw SQL concatenation was found. Other systemic issues are missing rate limiting, missing webhook replay protection, no centralized security headers/middleware, coarse admin authorization, external AI PII exposure risk, public telemetry ingestion/reads, and weak media trust boundaries.

No secrets were printed or live credentials tested. Secret quality, Vercel environment values, production database policies, storage ACLs, and provider console settings remain unverified.

## 30. Reliability

Only six runtime transaction uses were found. Many multi-entity workflows use sequential writes plus partial best-effort error handling. There is no outbox, queue, worker, retry registry, dead-letter queue, or distributed job lease framework. Some reminder automation uses advisory locks and transactions, which is a useful pattern, but execution is often triggered synchronously by reads or manually/cron.

External AI and WeChat OAuth calls have timeouts; WeChat Pay native API calls lack an explicit timeout. There is no circuit breaker, bulkhead, standardized retry policy, or request-wide deadline. Serverless connection limits are conservative, but frequent session last-seen writes and synchronous automation can amplify database load.

## 31. Observability

`runtime_events`, release incidents/alerts/audits, health/readiness/version endpoints, and operational summaries provide an application-level observability foundation. Logging otherwise relies primarily on `console.error`.

No structured logger, correlation/request ID middleware, OpenTelemetry traces, metrics exporter, SLO/error-budget model, sampling/redaction policy, or alert-delivery integration was found. Observability reads and event ingestion are public, enabling information disclosure and telemetry poisoning. Classification: **PARTIAL/WEAK**.

## 32. Operational Controls

Feature flags, runtime controls, release channels, release approvals, rollout guard policies/events, release incidents, smoke/readiness routes, UI acceptance records, and a cron secret are implemented. Admin mutation routes generally check admin; the rollout cron checks `CRON_SECRET`.

Controls remain database-state features rather than a proven deployment safety system. There is no evidence in source of signed approvals, two-person release authorization, automatic rollback execution, immutable control-plane audit, or alert provider. `CRON_SECRET` and release-channel variables are not fully represented in `.env.example`.

## 33. Test Coverage

No conventional unit, integration, contract, migration, concurrency, or end-to-end test files were found. There are 120 `verify-*` scripts plus smoke/runtime scripts, largely release-specific static assertions. These are valuable regression checks but do not substitute for behavioral tests against disposable infrastructure.

- Migration/seed/smoke/runtime scripts: not run because source-only audit constraints prohibit possible database, network, or state mutation.

Priority tests are authorization-denial matrices, tenant cross-access, fresh/upgrade migration replay, request/payment concurrency, duplicate webhooks, refresh/exchange replay, money invariants, and vertical contract tests.

## 39. Production Blockers

Production approval requires all P0 items to be closed and independently verified. At minimum:

1. Deny unauthenticated/cross-tenant access for request, organization, service, media, payment, support, notification, analytics, observability, and tracking routes.
2. Remove the public `force` transition path and make all request/payment/delivery state changes authorized, versioned, and transactional.
3. Reconcile the live schema read-only, replace split migrations with one ledgered canonical sequence, and prove fresh plus upgrade replay.
4. Add financial transaction boundaries, unique provider event handling, replay-safe webhooks, and an immutable accounting basis before processing real funds.
5. Close refresh and exchange replay races and deploy abuse-rate controls.
6. Add executable authorization, tenancy, migration, replay, concurrency, and financial-invariant tests.

Until those conditions are met, **19.0.0 must not be deployed or advertised as production-ready**.

## 40. Recommended Target Architecture

Retain a modular monolith initially; a microservice split would add operational risk before boundaries are trustworthy.

Recommended layers:

1. **HTTP boundary**: route schemas, request IDs, rate limits, secure headers, consistent errors.
2. **Identity/policy**: one session authenticator and deny-by-default action/resource/tenant authorization engine.
3. **Application commands**: idempotent use cases with explicit actor, tenant, expected version, and transaction.
4. **Domain modules**: identity, catalog, orders, delivery, payments/ledger, messaging, support, partner, operations, then normalized vertical extensions.
5. **Persistence**: one canonical Drizzle schema/migration chain, tenant-scoped repositories, optimistic concurrency, database constraints, optional RLS.
6. **Async boundary**: transactional outbox, leased workers, retry policy, DLQ, notification/provider adapters.
7. **Financial core**: immutable journal entries and provider events; derived balances; explicit refunds, payouts, disputes, and reconciliation.
8. **Observability/control plane**: structured redacted logs, traces, metrics, audit events, SLOs, signed/dual-control high-risk operations.

Public tracking or guest workflows should use narrow, expiring, revocable capabilities rather than raw entity identifiers. JSONB should remain only for non-critical extensibility, not authoritative lifecycle or money state.

## 41. Proposed First Implementation Sprint

**Sprint objective: establish a secure, reproducible backend foundation without adding vertical features.**

| Order | Work item | Acceptance criteria |
|---:|---|---|
| 1 | Freeze and inventory exposed legacy routes | Machine-readable route/method/auth/action/resource/tenant matrix; all P0 endpoints assigned an owner |
